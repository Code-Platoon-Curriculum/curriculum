# Connecting it All

## Intro

You've built a React + Vite frontend that looks and feels like a real application. You've explored a live PostgreSQL database in Supabase and sent real HTTP requests to its API using Postman. But those two sides have been living in isolation — your UI is still working with hardcoded or in-memory data, and your database has no idea your frontend exists.

This lecture closes that gap. By the end, your React application will be reading from and writing to your Supabase database. Every task created in the UI will persist. Every change will survive a page refresh. Your application will behave like a real full-stack product.

---

## Lesson

### What Do We Have?

Before we connect anything, it's worth being precise about what we're starting with on each side.

**Your React + Vite frontend** is currently a static site. It renders UI, manages local component state, and might even simulate CRUD with hardcoded arrays. But it has no memory — refresh the page and everything resets. Nothing is actually stored anywhere. It has zero awareness of your Supabase project.

**Your Supabase backend** is a fully capable dynamic system that's been running and waiting the whole time:

- A **PostgreSQL database** with your `users` and `tasks` tables already defined
- A **RESTful API** powered by PostgREST, auto-generated from your schema, with endpoints ready to handle every CRUD operation
- **API documentation** auto-generated by Supabase and accessible from your project dashboard — it describes every endpoint, every filter, and every expected response for your specific schema
- **API keys** — a publishable (anon) key that is safe to use from client-side code

Everything on the Supabase side is ready. The only work left is on the client side: teaching your React application when and how to talk to it.

---

### The Full Stack Workflow

Once connected, every user action in your UI will trigger a chain of events that spans all three layers of your stack. Understanding this flow is essential — it's the mental model that will guide every feature you build from here on.

```
User Action (click "Add Task")
    │
    ▼
React Component (calls a service function)
    │
    ▼
API Service Layer (builds and sends the HTTP request via axios)
    │
    ▼
Supabase PostgREST API (validates the request, checks the API key)
    │
    ▼
PostgreSQL Database (executes INSERT, returns the new row)
    │
    ▼
API Service Layer (receives the response)
    │
    ▼
React Component (updates state → UI re-renders)
```

A few things to note about this flow:

**Components never talk to the API directly.** There is always a dedicated service layer in between. This keeps your components focused on UI and user interaction, and keeps all your Supabase-specific logic in one place. If your API URL or key ever changes, you update one file — not every component.

**Every request is asynchronous.** Network calls take time. Your UI must account for three possible states after initiating a request: loading (waiting for the response), success (data came back), and error (something went wrong). A real application always handles all three.

**The database is the source of truth.** After a successful write (POST, PATCH, DELETE), your UI should reflect what the database actually contains — either by using the response data returned from the request, or by re-fetching. Never assume the local state is correct without confirmation from the server.

### What is Axios?

Axios is an HTTP client library for JavaScript. It's what your React application will use to send requests to your Supabase API.

The browser has a built-in way to make HTTP requests called `fetch`. Axios is an alternative that the developer community widely prefers for application code because it handles several things more cleanly:

- **Automatic JSON parsing** — `fetch` requires you to call `.json()` on the response manually; axios returns parsed data directly
- **Cleaner error handling** — `fetch` only throws on network failures; axios throws on any non-2xx status code, which means your `catch` block actually catches API errors
- **Request and response interceptors** — you can attach headers (like your API key) once at the axios instance level rather than on every individual request
- **Cleaner syntax** — axios methods (`axios.get`, `axios.post`, `axios.patch`, `axios.delete`) map directly to the HTTP methods you already know

You will configure a single axios instance for your project with your Supabase URL and API key baked in. Every service function then uses that instance — no headers duplicated, no URLs hardcoded in components.

#### Adding Axios to Your NPM Project

Axios is an npm package. Install it from your project's root directory:

```bash
npm install axios
```

### Environment Variables

Your environment variables live in a `.env` file at the project root:

```text
VITE_SUPABASE_URL=https://<your-project-id>.supabase.co
VITE_SUPABASE_ANON_KEY=<your-publishable-key>
```

> **Important:** Add `.env` to your `.gitignore` file. Never commit API keys to version control — even public (anon) keys.

Vite exposes environment variables prefixed with `VITE_` to client-side code via `import.meta.env`. Any variable without that prefix is ignored by Vite and won't be available in your components.

### Leveraging Claude Code

At this point in your project, you have a functioning React + Vite application with an established UI and user experience. The changes ahead are entirely within the client-side codebase — no backend modifications, no database schema changes, no new tables. You're wiring up existing components to an existing API.

This is a well-defined task with a clear scope, and it's exactly the kind of work that Claude Code handles well when given the right context. You already have Claude Code running in your project. Rather than making these changes manually file by file, you're going to hand Claude Code a precise, structured prompt that gives it everything it needs to do this work correctly and safely.

**Why a structured prompt matters here:**

Claude Code is an agent — it will read your codebase, form a plan, and execute changes. The quality of that plan depends entirely on the quality of the context you provide. A vague instruction like "connect my app to Supabase" will produce a guess. A structured prompt with your schema, your URL, your key, your constraints, and your explicit requirements will produce a plan you can review before a single line of code changes.

The prompt below is designed to:

1. Give Claude Code the full context it needs (schema, URL, key, resources)
2. Force it to analyze before acting (preventing premature code changes)
3. Set hard constraints that protect what's already working (preserve UI, don't introduce auth, don't redesign components)
4. Define the architecture it must follow (service layer, environment variables, axios)
5. Require it to surface ambiguities before proceeding

---

**Here is the prompt you will use:**

```
This React + Vite application using React Router DOM is functioning correctly
and I want to preserve the existing UI and user experience.

Resources:

1. SQL Schema: @./<path_to_exported_sql>
2. Supabase Project URL: <project_url>
3. Supabase Public API Key: <anon_key>
4. Resources: tasks and users

Requirements:

* Analyze the current application before making any code changes.
* Identify all existing CRUD flows and components that manage data.
* Present an implementation plan before modifying code.

Implementation Requirements:

* Preserve the existing UI.
* Replace all mock/local CRUD operations with Supabase API interactions.
* Use axios for all API communication.
* Create a dedicated API service layer.
* Components should never directly call axios.
* Store API configuration in environment variables.
* Implement loading, error, and success states for all CRUD actions.
* Ensure all UI changes remain synchronized with the Supabase backend.
* Analyze the SQL schema and correctly implement any relationships between
  tasks and users.
* Do not implement authentication at this time.
* Do not introduce unnecessary architectural changes or redesign existing
  components.

Deliverables:

1. Analysis of current architecture.
2. Proposed implementation plan.
3. Code changes.
4. Summary of modified files.
5. Any assumptions made during implementation.

Before writing code, tell me if you identify any ambiguities, missing schema
information, or architectural concerns.
```

**Before running this prompt, fill in three things:**

| Placeholder | Where to find it |
|---|---|
| `<path_to_exported_sql>` | Export your schema from Supabase → Database → Schema → Export. Save it to your project root. |
| `<project_url>` | Supabase Dashboard → Project Settings → API → Project URL |
| `<anon_key>` | Supabase Dashboard → Project Settings → API Keys → Publishable key |

The `@./` prefix before the SQL file path is Claude Code's syntax for attaching a file from your project as context. Claude Code will read the schema and use it to understand the relationship between `users` and `tasks` before writing any service logic.

---

**What to expect from Claude Code's response:**

Claude Code will not immediately start changing files. The prompt instructs it to analyze first and present a plan. You should expect:

1. **Architecture analysis** — a summary of what components exist, which ones manage data, and what mock/local state they currently use
2. **Implementation plan** — which files it intends to create (the service layer), which files it will modify (components), and how it plans to handle the `users`/`tasks` relationship
3. **A question or clarification** — if your schema has anything ambiguous (nullable foreign keys, missing constraints, naming inconsistencies), it will ask before proceeding

Review the plan before approving. If anything in the plan conflicts with your understanding of the application — a component it misidentified, a relationship it got wrong, a file it shouldn't touch — correct it in your reply before the code changes begin. This review step is the primary benefit of requiring the plan upfront.

Once you approve the plan, Claude Code will execute the changes, then deliver a summary of every modified file and any assumptions it made. Read the assumptions — they often surface decisions worth verifying.

## Conclusion

Your React + Vite frontend and your Supabase backend were always meant to be two halves of the same application. This lecture connects them.

The pattern you've established here — a configured axios instance, a dedicated service layer, components that consume service functions, environment variables for configuration — is not just a solution for this project. It is the standard architecture for client-side API integration. You'll use this same pattern in every full-stack project you build.

From this point forward, your application has memory. Data persists. Multiple users can interact with the same backend. You're no longer building a prototype — you're building a real product.
